# Smart Planning parity

The [original HTML prototype](prototype/index.html) loads its own CSS and JavaScript. Its active My Plan route runs through [app.js](prototype/js/app.js), [plan.js](prototype/js/pages/plan.js), and [smartPlan.js](prototype/js/pages/smartPlan.js). The prototype remains the functional reference for scheduling and is unchanged by this refinement.

## Reusable rules and migration adapters

- Use [smartSchedule.js](prototype/js/smartSchedule.js) as the primary scheduling reference. Port interval merging, protected time subtraction, workday and daily limits, focus-first slot selection, dependency checks and reason generation as deterministic functions. Pass a Singapore-aware clock, normalised intervals and authorised records explicitly. The prototype reads seeded state and a fixed demo clock.
- Port [schedulePreferences.js](prototype/js/schedulePreferences.js) validation and weekday lunch lookup. Preserve defaults, interval ordering and legal time bounds. PostgreSQL should own production preferences.
- Reuse [taskIntelligence.js](prototype/js/taskIntelligence.js) deadline selection and factor explanations. The active scheduler orders by effective deadline, manual priority and task ID. [ai.js](prototype/js/ai.js) supplies a separate numeric explanation with proposed demo weights. Keep those paths distinct until EM Services confirms any production changes, including precedence between hard safety or statutory constraints and other recorded concerns.
- Port [planningIssues.js](prototype/js/planningIssues.js) and [scheduleReview.js](prototype/js/scheduleReview.js) as backend validation and review rules. Replace in-memory draft state, demo-date fingerprints and local storage with versioned input snapshots, transactional writes and an audit trail. Use the same preflight rules for proposed moves and final acceptance.

## Phase 2 implementation plan

1. Confirm the client rules for prioritisation, fixed-duty conflicts and unknown availability. Confirm whether any legacy planner strategies are required. Record the active prototype outputs as migration fixtures before modifying ordering.
2. Define canonical inputs for duties and eligible case or task work. Add scoped PostgreSQL preferences, draft and accepted-block storage, audit history and versioned inputs. Keep the current Phase 1 duty API compatible.
3. Port the deterministic scheduler and validation once into the backend. Add transactional checks for fixed SyncAI overlaps, including concurrent writes. Decide how the service receives availability with least privilege. Preserve an explicit unknown state whenever Outlook availability is missing, partial or stale.
4. Add a review overlay in the existing calendar for daily and weekly proposals, capacity, priority reasons, unscheduled reasons and suggested corrective actions. Add accessible controls and drag-and-drop for flexible proposals with immediate feedback from the same validation rules.
5. Implement revision-checked acceptance and rejection, duplicate prevention, saved accepted blocks, and the manager request and escalation workflow. Verify that rejecting a draft leaves the accepted schedule and source duties intact.
6. Run parity, authorization, concurrency and restart tests. Verify the complete workflow with isolated PostgreSQL data and a consented Microsoft test mailbox before deployment.
